ABF0 hardware spike Measures what the ears actually do, not what the docs claim. Open in Windows Chrome — Web Bluetooth has no adapter inside WSL2. Every action appends to the log; use Copy log at the end.

1 · Connect

The ears advertise the 16-bit UUID (0x03 0x03 F0 AB) and the complete local name, so both filters should work. Try both — which one wins decides what the web app ships.

not connected

2 · Discover

Records every reachable characteristic and its property flags. The firmware declares ABF2 as READ + INDICATE while sending unconfirmed notifications — this is where that shows up.

3 · Read & subscribe ABF2

CCCD 01 00 means Chrome enabled notifications, 02 00 means indications. The firmware sends with need_confirm = false either way.

4 · Lighting write (safe, observable)

Packet 02 <mode> <speed> 01 RR GG BB — 7 bytes, solid mode. If the LEDs change, the write path works end to end.

5 · Write-with-response probe

ABF1 is WRITE_NO_RESPONSE only today. Expected to reject — the point is to record how it fails, since the store protocol needs this property added in firmware.

6 · Raw size probe (ATT layer)


Payloads start with type byte 0x00, which the firmware's unpack rejects — the ears ignore them entirely. This measures only whether the browser throws, which answers "are oversized writes silently dropped or surfaced as an error".

7 · Delivery ceiling (the real question)

Sends a complete one-chunk custom animation of K keyframes. The firmware refuses to play a truncated payload (data_len < 1 + count × 12), so the ears moving is proof every byte arrived. Ramp K until they stop moving, and mark each result.

= 65 bytes
42 keyframes = 509 bytes, the largest single chunk that fits the 512-byte attribute.
