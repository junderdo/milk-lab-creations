# DB client, ORM, and migration tooling for Aurora DSQL

Research date: 2026-08-02. Follow-up to `research/aurora-dsql-compatibility.md`
(GO verdict on DSQL). Question: which Postgres client, ORM, and migration
tooling should this app (tRPC v11 on Lambda, SST v3, pnpm monorepo, hobby
scale) adopt for DSQL?

## RECOMMENDATION

**Client:** `@aws/aurora-dsql-node-postgres-connector` (`AuroraDSQLPool`, a
drop-in extension of `pg.Pool`) — module-scope pool in the Lambda handler.
**ORM:** Prisma ORM v7+ with the Rust-free client (`queryCompiler` +
`driverAdapters`, GA in v7) via `@prisma/adapter-pg` on top of the connector.
**Migrations:** `@aws/aurora-dsql-prisma-tools` (`aurora-dsql-prisma migrate`)
to generate DSQL-compatible SQL, applied with
`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK=1 npx prisma migrate deploy` from CI (a
single runner).

Why this combination for this stack:

- **It is the only officially supported end-to-end path.** AWS announced
  Prisma support on 2026-02-25 and maintains the validator/transformer
  (awslabs/aurora-dsql-orms) and the connector (awslabs/aurora-dsql-connectors)
  themselves. Every DSQL quirk from the compatibility research — no FKs, async
  indexes, 1 DDL per transaction, IAM tokens, OCC retries — is handled by an
  AWS-maintained tool instead of hand-rolled code.
- **Lambda cold starts are fine now.** The historical objection to Prisma on
  Lambda (a ~14 MB Rust query engine binary) is gone: the Rust-free client is
  GA in Prisma 7, ~1.6 MB (about 90% smaller), with faster cold starts — and
  it *requires* driver adapters, which is exactly the DSQL connection mode
  anyway.
- **tRPC synergy.** Prisma's generated types flow directly into tRPC v11
  procedure outputs; `relationMode = "prisma"` gives typed relations while
  respecting DSQL's no-FK rule.
- **Hobby-scale ergonomics.** One schema file, `aurora-dsql-prisma migrate`
  emits reviewable SQL, `prisma migrate deploy` tracks applied migrations.
  The `AuroraDSQLPool` handles token generation per connection and ships an
  OCC `transaction()` retry helper, which DSQL's optimistic concurrency makes
  mandatory sooner or later.

Caveats to accept: no `prisma migrate dev` / shadow-database flow (generate
via the AWS CLI tool instead), some auto-fixes are behavior-changing
(`WARNING`s must be reviewed — e.g. an async index is not ready when the
statement returns), and `DROP CONSTRAINT` diffs need manual editing.

## Runner-up: Kysely + connector + hand-managed migrations

Kysely over the same `AuroraDSQLPool` works today (it is just a typed query
builder over `pg`) and is lighter than Prisma at runtime. It was not chosen
because **you inherit the whole migration problem**:

- Kysely's `Migrator` with `PostgresDialect` acquires `pg_advisory_lock`
  before migrating (`src/dialect/postgres/postgres-adapter.ts`), and DSQL does
  not support advisory locks — the migrator fails unless you subclass the
  dialect adapter to no-op the lock.
- The migrator wraps each migration in a transaction because
  `supportsTransactionalDdl` is `true` for Postgres — any migration with two
  DDL statements violates DSQL's 1-DDL-per-transaction rule. You must pass
  `disableTransactions: true` and keep every migration to safe statements.
- No schema builder support for `CREATE INDEX ASYNC` — raw `sql` template
  strings, and something must poll the async index job.
- No codegen of a schema — you maintain the TypeScript `Database` interface
  (or add kysely-codegen) yourself.

Viable, and a reasonable fallback if Prisma's abstraction ever chafes, but at
hobby scale the AWS-maintained Prisma path is less total machinery to own.
If chosen: run `dsql-lint` over every migration in CI.

## Findings

### 1. Prisma + DSQL: maturity and mechanics

**Official since 2026-02-25** ("Aurora DSQL launches new support for Tortoise,
Flyway, and Prisma") — AWS-built, Apache-2.0, in awslabs monorepos with
independent versioning.

**What `@aws/aurora-dsql-prisma-tools` actually does** (README,
awslabs/aurora-dsql-orms `node/prisma`):

- `validate` — checks the Prisma schema for DSQL compatibility; specifically
  requires `relationMode = "prisma"` (no FK constraints), then generates SQL
  from the schema and delegates all SQL checks to `dsql-lint`.
- `transform` — runs `dsql-lint --fix` over Prisma-generated migration SQL.
- `lint` — reports DSQL issues without modifying.
- `migrate` — all-in-one: validate, `prisma migrate diff`, transform, write
  `prisma/migrations/NNN_name/migration.sql`. `--from-config-datasource`
  diffs against the live database (via `prisma.config.ts` credentials) for
  incremental migrations.

The underlying `dsql-lint` (awslabs/aurora-dsql-tools, Rust binary bundled in
the npm package) parses SQL and auto-fixes: `SERIAL` → `BIGINT GENERATED BY
DEFAULT AS IDENTITY (CACHE 1)`, removes `FOREIGN KEY`/`REFERENCES` (WARNING),
rewrites indexes to `CREATE INDEX ASYNC` (WARNING: not ready on return),
splits multi-DDL transactions into one-DDL `BEGIN/COMMIT` blocks. Unfixable
cases error out (e.g. `ADD COLUMN ... DEFAULT/NOT NULL`, `DROP CONSTRAINT`)
and need manual splitting/backfill. It self-describes as an early release —
"most commonly encountered compatibility issues."

**Applying migrations:** standard `prisma migrate deploy`, but with
`PRISMA_SCHEMA_DISABLE_ADVISORY_LOCK=1` because DSQL lacks advisory locks.
Prisma's `_prisma_migrations` bookkeeping table works normally. The AWS blog's
schema requirements: `relationMode = "prisma"`, UUID PKs via
`@default(dbgenerated("gen_random_uuid()")) @db.Uuid`, no `autoincrement()`.
Multi-region: run migrations once per cluster — DSQL replicates schema to
peered regions.

**Known limitations:** no `prisma migrate dev` (needs lock-free handling), no
shadow database, migration *generation* goes through the AWS CLI tool rather
than Prisma's native dev loop, and the token-refresh/connection concerns are
delegated entirely to the connector (Prisma tools do none of that — they are
build-time only).

**Bundle size / cold start:** Prisma's Rust-free client (enable generator
`previewFeatures = ["queryCompiler", "driverAdapters"]` on 6.7–6.x; GA and
default-capable in 7.0.0) replaces the Rust query engine with a TypeScript
query compiler: ~90% smaller bundle (~14 MB → ~1.6 MB), faster cold starts and
lower memory on Lambda, up to 3.4x faster queries by removing cross-language
serialization. Driver adapters are mandatory in this mode — which DSQL
requires anyway (`@prisma/adapter-pg` wrapping the AWS connector pool).

- https://aws.amazon.com/about-aws/whats-new/2026/02/aurora-dsql-launches-tortoise-flyway-prisma
- https://github.com/awslabs/aurora-dsql-orms (node/prisma README)
- https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint
- https://aws.amazon.com/blogs/database/building-a-multi-region-api-with-prisma-orm-and-amazon-aurora-dsql/
- https://www.prisma.io/blog/try-the-new-rust-free-version-of-prisma-orm-early-access
- https://www.prisma.io/blog/prisma-orm-without-rust-latest-performance-benchmarks

### 2. Kysely + DSQL

Setup: `PostgresDialect` fed an `AuroraDSQLPool` (or a plain `pg.Pool` whose
`password` is an async function calling `DsqlSigner.getDbConnectAuthToken()`
from `@aws-sdk/dsql-signer` — node-postgres accepts a function that is invoked
per new connection). No official Kysely/DSQL adapter exists in AWS's list.

Migrations are the weak point (verified against kysely-org/kysely source,
`src/migration/migrator.ts` and `src/dialect/postgres/postgres-adapter.ts`):

- `PostgresAdapter.acquireMigrationLock` runs `select pg_advisory_lock(...)` —
  **unsupported on DSQL**; requires a custom dialect adapter override.
- `supportsTransactionalDdl` is `true` for Postgres, so the Migrator wraps
  each migration in a transaction — collides with 1-DDL-per-transaction unless
  `disableTransactions: true` is set and each migration is kept to one DDL (or
  written as sequential single statements).
- `CREATE INDEX ASYNC` and job polling (`sys.jobs`) must be raw SQL.
- The migration/lock tables themselves (`kysely_migration`,
  `kysely_migration_lock` with a row-update lock) are plain DML and fine.

Verdict: excellent runtime, DIY migration harness.

- https://kysely.dev/docs/migrations
- https://github.com/kysely-org/kysely/blob/master/src/dialect/postgres/postgres-adapter.ts
- https://github.com/kysely-org/kysely/blob/master/src/migration/migrator.ts
- https://docs.aws.amazon.com/aurora-dsql/latest/userguide/SECTION_Node-js-connectors.html

### 3. Drizzle + DSQL: currently a trap for migrations

drizzle-team/drizzle-orm issue #5248 ("[FEATURE]: AWS DSQL Support", opened
2026-01-11) is **still open** as of 2026-08-02: no assignee, no linked PRs, no
maintainer commitment beyond "probably after v1 release"; it exists to collect
pains and workarounds (see also discussion #3677). No Drizzle adapter appears
in AWS's official connector/ORM lists.

Generic-Postgres mode: the drizzle-orm *runtime* (node-postgres driver) works
against DSQL if the schema avoids `references()`. But drizzle-kit is the trap:
`drizzle-kit generate` emits plain `CREATE INDEX` (no ASYNC), `REFERENCES`
clauses for any declared relations, and `drizzle-kit migrate` executes
migration files transactionally with multiple DDL statements — all three
violate DSQL rules. You would have to hand-edit every generated migration or
pipe each through `dsql-lint --fix` and apply with a custom runner, at which
point Drizzle's main workflow advantage is gone. Revisit after v1/#5248.

- https://github.com/drizzle-team/drizzle-orm/issues/5248
- https://github.com/awslabs/aurora-dsql-orms (no Drizzle package)
- https://github.com/awslabs/aurora-dsql-tools/tree/main/dsql-lint (fix rules)

### 4. Raw pg + generic migration runners

- **Atlas (atlasgo.io): explicit DSQL support** — the only third-party
  migration tool with a dedicated DSQL guide (declarative + versioned flows).
  But it is **Pro-tier only** (paid) and documents that DSQL's missing
  advisory locks mean Atlas cannot lock against concurrent migration runs.
  Overkill/cost-inappropriate for a hobby app.
- **node-pg-migrate:** no DSQL support mentioned anywhere in its docs; it
  wraps migrations in transactions by default (per-migration opt-out exists)
  and emits plain `CREATE INDEX` / FK constraints from its builder API —
  usable only in raw-SQL mode with the same hand-holding as Drizzle.
- **dbmate:** no DSQL support found in docs or issues.
- **Flyway: official AWS plugin** (`software.amazon.dsql:aurora-dsql-flyway-support`,
  Maven Central, in awslabs/aurora-dsql-tools) — runs each schema change in
  its own transaction, handles IAM auth, documents OCC instead of advisory
  locks. Real, but a JVM toolchain in a pnpm/TS monorepo; not a fit here.

- https://atlasgo.io/guides/dsql/automatic-migrations
- https://github.com/awslabs/aurora-dsql-tools/tree/main/flyway
- https://www.npmjs.com/package/node-pg-migrate

### 5. AWS's own recommended migration patterns

From the DSQL migration guide, the Flyway plugin docs, and the Prisma blog:

- One DDL statement per transaction; never mix DDL and DML in a transaction.
- Always `CREATE INDEX ASYNC`; poll the returned job for completion before
  depending on the index.
- Run migrations **from a single instance/runner** — DSQL has no advisory
  locks, so tools cannot mutually exclude concurrent migrators; serialize in
  CI instead.
- Multi-region clusters: apply migrations once; DSQL replicates DDL to peers.
- Referential integrity in the application layer; UUID PKs for distribution.
- AWS's published tooling stack: `dsql-lint` (universal SQL fixer),
  Flyway plugin (Java), Prisma tools (Node), Django/SQLAlchemy/Tortoise
  (Python), EF Core (.NET), Hibernate (Java) — Prisma is the only Node ORM
  with first-party migration tooling.

- https://docs.aws.amazon.com/aurora-dsql/latest/userguide/working-with-postgresql-compatibility-migration-guide.html
- https://github.com/awslabs/aurora-dsql-tools
- https://github.com/awslabs/aurora-dsql-orms
- https://aws.amazon.com/blogs/database/building-a-multi-region-api-with-prisma-orm-and-amazon-aurora-dsql/

### 6. Connection lifecycle on Lambda

- **Tokens:** IAM auth tokens default to 15-minute expiry (configurable up to
  1 week). The token is only checked at connection time — "After the
  connection is established, the connection remains valid even if the
  authentication token expires." Generation is a local SigV4 signing
  operation (no network call, negligible cost).
- **Connections:** hard cap of 60 minutes per connection; 10,000 per cluster;
  100 new connections/s. AWS's pooling guidance: cap pool max-lifetime around
  55 minutes with jitter so the pool recycles before the 1-hour kill.
- **Lambda pattern (AWS blogs):** create the pool at **module scope** so warm
  invocations reuse connections; connection establishment from Lambda costs
  ~600–870 ms (TLS + auth), which reuse reduces to zero. Fresh token per new
  connection is handled by the connector automatically.
- **Officially recommended client:** `AuroraDSQLPool` from
  `@aws/aurora-dsql-node-postgres-connector` — extends `pg.Pool`, generates a
  token for every new connection (admin vs regular token chosen by username),
  auto-detects region from the hostname, supports all `pg.Pool` options plus
  `tokenDurationSecs`, custom credential providers, and OCC retry
  (`pool.transaction(cb, { maxRetries })`, backoff on `OC000`/`OC001`/`40001`).
  For this app: small pool (`max: 2–3`), `idleTimeoutMillis` ~60 s, host/user
  from SST's linked `Resource.<Cluster>.endpoint`.
